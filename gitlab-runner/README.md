# GitLab Runner on Rocky Linux

The init installs only the base host: Docker, GitLab Runner, admin tools, security updates and no password logins. Login stays as Hetzner sets it up: root with your SSH key on port 22. Nothing in the init can lock you out (`tools/test-cloud-init.py` checks that). Everything else, including the users below, is installed afterwards, component by component, in either of two ways:

- **A. Script**: `sudo gitlab-runner/setup.sh --<component>`. It checks prerequisites, keeps the right order and skips what is already installed.
- **B. Copy-paste**: self-contained blocks in [`COMMANDS.md`](COMMANDS.md), one per component. They create the files and install, no repo copy needed.

| File | Purpose |
|---|---|
| `cloud-init-rocky.yaml` | user-data for a new server: SSH hardening, Docker, GitLab Runner, security updates, admin tools, aliases, tmux config (generated) |
| `setup.sh` | installs components (variant A); `--list` shows what is installed |
| `register.sh` | registers the runner (asks for the `glrt-` token); wrapper over `install/register-runner.sh` |
| `update.sh` | updates installed components to the repo state; wrapper over `install/update.sh` |
| `COMMANDS.md` | copy-paste blocks (variant B), generated by `tools/render-paste-commands.py` |

## Plan: what to apply, in which order

### New server (created with `cloud-init-rocky.yaml`)

Do the steps top to bottom. Each step has a check; go on only when it passes. Steps marked *optional* can be skipped or done later, in any order among themselves, as long as their prerequisite is in place. `A` is the script from a repo copy (step 2), `B` is the block in [`COMMANDS.md`](COMMANDS.md).

Shortcut for steps 3a, 4, 5 and 7–11: `sudo gitlab-runner/setup.sh --all` asks for the token once and runs them in this order. B has the same as [Everything at once](COMMANDS.md#all).

After that, nothing is manual: security updates, the weekly cleanup and the disk guard run on their own. Regular work is `health -q` now and then, and the update (section 4) when the repo changes.

### Existing server (older init, root login)

The order matters here, because of SSH access. Steps and rollback are in [Moving an existing server to these users](#moving-an-existing-server-to-these-users):

1. As root: `install/users.sh` or the [Users](COMMANDS.md#users) block.
2. Test `ssh ops@SERVER_IP 'sudo -n true && echo ok'` from a second terminal, with the root session still open.
3. `sudo gitlab-runner/update.sh`, which moves the runner and the stacks to the service users.
4. `sudo install/lock-root.sh` or the [Lock root SSH](COMMANDS.md#lock-root) block.
5. Then continue with the new-server plan from step 4, for whatever isn't installed yet (`sudo gitlab-runner/setup.sh --list`).

## Users

| User | Kind | SSH | What it does |
|---|---|---|---|
| `ops` | admin | yes, by key | your login; `sudo` without password; not in the `docker` group, so Docker needs `sudo` |
| `gitlab-runner` | service | no (`nologin`, no password) | the runner service runs as this user; Docker access through the `docker` group, which the executor needs |
| `monitoring` | service | no (`nologin`, no password) | Prometheus, node_exporter, Grafana, Loki and Alloy run as this user; it reads their config (`root:monitoring`, `0640`) but cannot change it |
| `root` | | by key, until you run `--lock-root` | the init does not change it |

SSH accepts keys only, and only from members of `ssh-users` (the admin). Local port forwarding (`ssh -L`, for the Grafana tunnel) works; remote forwarding, agent and X11 forwarding are off. All of this is set by `install/users.sh` (`setup.sh --users`, plan step 3a). It is not part of the init.

The admin is `ops` on every OS. Set `ADMIN_USER=...` to use another name, or `SSH_PORT=...` for another port, with `install/users.sh`.

A shortcut for your laptop's `~/.ssh/config`, then use `ssh runner`, `scp file runner:` and so on:

```text
Host runner
  HostName SERVER_IP
  User ops
```

Why this split: GitLab's [runner security docs](https://docs.gitlab.com/runner/security/) warn that anyone with the Developer role in a project can compromise the runner host. Docker's [security docs](https://docs.docker.com/engine/security/) say only trusted users should control the daemon. So nobody you log in as is in the `docker` group, and the services don't run as root.

## 1. Create the server

1. **GitLab**: Settings → CI/CD → Runners → New runner. Set tags and "run untagged jobs", then copy the `glrt-` token. It is shown once.
2. **Hetzner Console**: Rocky Linux, your SSH key, paste `gitlab-runner/cloud-init-rocky.yaml` as Cloud config. Firewall: inbound TCP 22 from your IP only, outbound left empty (allow all).
3. **Wait for cloud-init**, as root with the key you gave Hetzner:

   ```bash
   ssh root@SERVER_IP 'cloud-init status --wait; cat /var/log/ci-bootstrap-failed.log 2>/dev/null; systemctl is-active sshd docker gitlab-runner'
   ```

   `done` and three `active` lines mean the base is ready. `ci-bootstrap-failed.log` lists optional tools that aren't in the repositories for this Rocky version, or a failed step.

What the init installs:

- The SSH drop-in `00-ci-hardening.conf`: no password or keyboard-interactive logins, root by key only, no X11. sshd checks it first (`sshd -t`); if it is rejected, the file is removed and the defaults stay, so login keeps working.
- Automatic security updates, journal size limit, timezone.
- Docker Engine and GitLab Runner (docker executor).
- Tools: `htop`, `btop`, `ncdu`, `iotop`, `mtr`, `nano`, `vim`, `rsync`, `wget`, `unzip`, `bash-completion`, `skopeo`, `restic`, `dnf-utils`, `dig`, `lsof`, `sysstat`, `tcpdump`, `traceroute`, `nc`, `tmux`, `jq`, `git`. Tools outside the base repositories come from EPEL. A missing one is logged and doesn't stop the boot.
- Aliases: `runner-logs`, `runner-errors`, `runner-jobs`, `runner-metrics`, `dfd`, `dstats`. tmux: mouse on, 50000 lines of history.

Not in the init, on purpose: users, closing root SSH, another SSH port, SELinux enforcing, running services as other users. They are separate steps in the plan above, so a mistake there never costs you the login.

## Moving an existing server to these users

For a server created with an older init, where you still log in as root. Do it in this order, so you never lose access:

1. Copy the repo (`scp -r server-init-config root@SERVER_IP:`), then `sudo ~/server-init-config/install/users.sh` as root, or paste the [Users](COMMANDS.md#users) block.
2. **Keep that session open** and test from a second terminal on your laptop: `ssh ops@SERVER_IP 'sudo -n true && echo ok'`. It must print `ok`.
3. Apply the update, so the stacks and the runner move to their service users: `sudo gitlab-runner/update.sh` (or the [Update](COMMANDS.md#update) block). It stops if a step fails and restores what it changed.
4. Lock root: `sudo install/lock-root.sh` (or the [Lock root SSH](COMMANDS.md#lock-root) block). From now on: `ssh ops@SERVER_IP`.

Rollback if the admin login fails: in the still-open session, `sudo install/users.sh --unlock-root` reopens root SSH; `rm /etc/ssh/sshd_config.d/00-ci-hardening.conf && systemctl reload sshd` goes back to the previous SSH rules entirely. The runner service goes back to root with `rm /etc/systemd/system/gitlab-runner.service.d/10-service-user.conf && systemctl daemon-reload && systemctl restart gitlab-runner`. Do that while no jobs are running.

### Renaming the admin to `ops` (server created when the admin was `rocky`)

Logged in as `rocky`:

```bash
sudo ADMIN_USER=ops ~/server-init-config/install/users.sh   # creates ops with root's keys and sudo; keeps the root lock
```

From a second terminal on your laptop, with the `rocky` session still open: `ssh ops@SERVER_IP 'sudo -n true && echo ok'`. It must print `ok`. Then, logged in as `ops`, remove the old admin (this deletes `/home/rocky`):

```bash
sudo gpasswd -d rocky ssh-users
sudo rm -f /etc/sudoers.d/90-rocky
sudo userdel -r rocky
```

## 2. Copy the repo to the server (variant A only)

From your laptop, in the folder that contains `server-init-config`. Repeat this every time the repo changes:

```bash
scp -r server-init-config ops@SERVER_IP:
ssh ops@SERVER_IP
cd ~/server-init-config
```

All commands below run on the server in `~/server-init-config`, with `sudo`. If a script says `Permission denied` (the copy lost its executable bits, for example from Windows), run `chmod +x gitlab-runner/*.sh install/*.sh scripts/*` once, or prefix the command with `sudo bash`.

## 3. Install components

### A. Script

```bash
sudo gitlab-runner/setup.sh --list                       # what is installed
sudo gitlab-runner/setup.sh --all                        # users, tools, runner, Docker Hub cache, monitoring, logging, npm and shared cache
sudo gitlab-runner/setup.sh --packages                   # only htop, btop, ncdu and the other admin tools
sudo gitlab-runner/setup.sh --register --monitoring      # or pick components
sudo DOMAIN=grafana.example.com ACME_EMAIL=you@example.com gitlab-runner/setup.sh --grafana-domain
sudo gitlab-runner/setup.sh --lock-root                  # after the admin login works
```

| Flag | Installs |
|---|---|
| `--base` | users + packages + tools + registry-cache + monitoring |
| `--all` | `--base` + register + logging + npm-cache + shared-cache |
| `--users` | admin user, service users, SSH hardening (root SSH stays open) |
| `--packages` | admin tools (htop, btop, ncdu, iotop, mtr, dig, tcpdump, restic, skopeo, sar, ...), aliases, tmux config |
| `--tools` | `health`, weekly cleanup, disk guard and their timers |
| `--register` | registers the runner (asks for the token) |
| `--registry-cache` | Docker Hub pull-through cache on `127.0.0.1:5000` |
| `--monitoring` | Prometheus, node_exporter, Grafana, as the `monitoring` user |
| `--logging` | Loki + Grafana Alloy, as the `monitoring` user: container logs and the journal in Grafana |
| `--npm-cache` | Verdaccio npm cache for jobs |
| `--shared-cache` | shared `/srv/ci-cache` for npm and Sonar |
| `--prewarm` | daily pre-pull of CI images (asks for a deploy token) |
| `--grafana-domain` | Grafana on HTTPS via Caddy (`DOMAIN`, `ACME_EMAIL`) |
| `--selinux` | SELinux enforcing, then checks Docker and the runner |
| `--lock-root` | closes root SSH; never part of `--all` |

Components are installed in that order whatever the order of the flags. If one fails, fix the cause and rerun the same command. Finished components are skipped.

### B. Copy-paste

[`COMMANDS.md`](COMMANDS.md) has one self-contained block per component, in the style of `sudo bash <<'INSTALL' ... INSTALL`. Paste a block into an SSH session as `ops` (as root before the [Users](COMMANDS.md#users) block has run). It writes the files it needs to `/root/server-init-config` and runs the installer, so it works without copying the repo. Blocks that ask for input (runner token, deploy token, update) run the installer on their last line, so the prompt reads from your keyboard and not from the rest of the paste.

| Block | What it does |
|---|---|
| [Base host](COMMANDS.md#base) | users, Docker, GitLab Runner and tools, the same as the init; only for a server created without it |
| [Users](COMMANDS.md#users) | admin user, service users, SSH hardening |
| [Admin tools](COMMANDS.md#packages) | htop, btop, ncdu, iotop and others, aliases, tmux config |
| [Health + cleanup](COMMANDS.md#tools) | `health`, weekly cleanup, disk guard |
| [Register](COMMANDS.md#register) | registers the runner (asks for the token) |
| [Docker Hub cache](COMMANDS.md#registry-cache) | pull-through cache on `127.0.0.1:5000` |
| [Monitoring](COMMANDS.md#monitoring) | Prometheus, node_exporter, Grafana |
| [Logging](COMMANDS.md#logging) | Loki + Grafana Alloy |
| [npm cache](COMMANDS.md#npm-cache) | Verdaccio for jobs |
| [Shared cache](COMMANDS.md#shared-cache) | `/srv/ci-cache` for npm and Sonar |
| [Image prewarm](COMMANDS.md#prewarm) | daily pre-pull of CI images |
| [Grafana domain](COMMANDS.md#grafana-domain) | HTTPS via Caddy |
| [SELinux](COMMANDS.md#selinux) | enforcing mode |
| [Lock root SSH](COMMANDS.md#lock-root) | closes root SSH, after the admin login works |
| [Update](COMMANDS.md#update) | updates everything installed |

`COMMANDS.md` is generated from the repo files, so a block always matches the scripts in the repo. After changing a file, run `tools/render-paste-commands.py`; `--check` fails if `COMMANDS.md` is stale.

## 4. Update

Copy the repo again (step 2), then:

```bash
cd ~/server-init-config
sudo gitlab-runner/update.sh --dry-run   # preview, changes nothing
sudo gitlab-runner/update.sh             # apply
sudo gitlab-runner/update.sh --os        # also OS packages, Docker and GitLab Runner; never reboots
sudo gitlab-runner/update.sh --rollback  # restore the files from the last backup
```

It syncs scripts, units and stack configs for what is installed. It backs up every changed file, restores them if a check fails, and skips CI-affecting steps while jobs are running (exit code `3`, rerun later). It also moves the monitoring and logging containers to the `monitoring` user, handing their data volumes over to it, so it needs `install/users.sh` to have run.

## Everyday commands

```bash
health            # sudo health: full report; health -q quick; health -c containers only
htop / btop       # processes
ncdu -x /         # what fills the disk (sudo ncdu -x / for everything)
runner-logs       # sudo journalctl -u gitlab-runner -f
runner-errors     # errors and warnings of the last 30 minutes
runner-jobs       # running job containers
runner-metrics    # runner metrics from 127.0.0.1:9252
dfd               # df -h / and sudo docker system df
dstats            # sudo docker stats --no-stream
sudo gitlab-runner list ; sudo gitlab-runner verify
sudo docker image prune -af --filter until=168h
```

### Cleanup

Installed by `--tools` (or the [Health + cleanup](COMMANDS.md#tools) block). The weekly run is on Monday 03:30; the disk guard checks every 30 minutes and runs an emergency cleanup with 1-day retention when `/` reaches 85%.

```bash
sudo DRY_RUN=1 runner-weekly-cleanup.sh            # show what would be removed, remove nothing
sudo runner-weekly-cleanup.sh                      # run now (skips the runner cache wipe while jobs run)
sudo RETENTION_DAYS=1 runner-weekly-cleanup.sh     # aggressive: keep only the last day
runner-weekly-cleanup.sh --help                    # all settings
systemctl list-timers 'runner-*' --no-pager        # next runs
sudo journalctl -t runner-weekly-cleanup --since "-7d" --no-pager | tail -40   # what it removed, disk before/after
sudo journalctl -t runner-disk-guard --since "-7d" --no-pager                  # emergency runs
```

To change the schedule, edit `systemd/runner-weekly-cleanup.timer` in the repo and run the update. The thresholds are environment variables of the scripts (`RETENTION_DAYS`, `SHARED_CACHE_MAX_AGE_DAYS`, `HARD_LIMIT`).

### Grafana, Prometheus and logs

All of them listen on `127.0.0.1` only. Reach them through an SSH tunnel from your laptop:

```bash
ssh -N -L 3000:127.0.0.1:3000 -L 9090:127.0.0.1:9090 ops@SERVER_IP
# Grafana    http://localhost:3000   user admin, password: sudo grep GF_SECURITY_ADMIN_PASSWORD /opt/monitoring/.env
# Prometheus http://localhost:9090
```

Logs: Grafana → Explore → Loki. Useful queries:

```text
{unit="gitlab-runner.service"}                 runner service log
{unit="gitlab-runner.service"} |~ "(?i)error|warn"
{unit="docker.service"}                        Docker daemon
{unit="sshd.service"} |= "Failed"              failed SSH logins
{compose_project="registry-cache"}             Docker Hub cache
{compose_project="monitoring"}                 Prometheus, Grafana, node_exporter
{source="journal", level=~"err|crit|alert|emerg"}
```

Job containers are not collected. Their output is already the job log in GitLab. Logs are kept for 7 days (`retention_period` in `logging/loki.yaml`).

### Change the runner config

```bash
sudo cp -a /etc/gitlab-runner/config.toml /etc/gitlab-runner/config.toml.bak.$(date +%Y%m%d-%H%M%S)
sudo nano /etc/gitlab-runner/config.toml    # concurrent, request_concurrency, pull_policy, volumes
sudo chown gitlab-runner:gitlab-runner /etc/gitlab-runner/config.toml
sudo gitlab-runner verify
sudo systemctl restart gitlab-runner        # do it while no jobs are running
```

`concurrent` is the number of jobs at once and `request_concurrency` is the number of parallel job requests to GitLab. Keep `concurrent` at or below the number of vCPUs. A CAX11 has 2.

`pull_policy = "if-not-present"` reuses images already on the host. GitLab's security docs allow that only on runners limited to trusted users and projects, which this one is. Switch to `always` if you ever attach projects you don't control.

### Remove or replace the runner

```bash
sudo gitlab-runner unregister --all-runners   # removes it from GitLab and from config.toml
```

Then delete the runner in GitLab if it still shows up, create a new one and register again.

## Check the first boot

```bash
cloud-init status --long
cat /var/log/ci-bootstrap-failed.log 2>/dev/null
sudo sshd -T | grep -Ei '^(port|passwordauthentication|permitrootlogin|allowgroups|allowtcpforwarding) '
ps -o user=,supgrp= -p "$(systemctl show -p MainPID --value gitlab-runner)"    # gitlab-runner ... docker
sudo docker ps --format 'table {{.Names}}\t{{.RunningFor}}' ; sudo docker inspect -f '{{.Name}} {{.Config.User}}' $(sudo docker ps -q)
grep -E '^(upgrade_type|apply_updates)' /etc/dnf/automatic.conf
uname -r ; rpm -q kernel-core                     # different versions mean a reboot is pending
```

If `/etc/dnf/automatic.conf` is missing, the DNF version uses a different config path or timer name. Set up automatic updates by hand using the official docs.

## Troubleshooting

- **`Connection timed out`**: the Hetzner Firewall has no inbound rule for TCP 22 from your current IP. Fix the rule in the Hetzner Console (it applies at once).
- **`Permission denied (publickey)` as `ops`**: the key was not copied, or you use another key. In a root or console session: `sudo cat /home/ops/.ssh/authorized_keys`, then `sudo install/users.sh` to copy root's keys again. `--lock-root` refuses to run while the admin has no key.
- **`sudo: health: command not found`**: the sudoers drop-in sets `secure_path` with `/usr/local/bin`. Check `sudo cat /etc/sudoers.d/90-ops`, or call `sudo /usr/local/bin/health`.
- **`Request bottleneck: request_concurrency=1` in the log**: the runner asks GitLab for one job at a time, so pickup is slow. `sudo grep request_concurrency /etc/gitlab-runner/config.toml`; registration sets it to 2. Add it under `[[runners]]` and restart if it is missing.
- **Jobs stay pending**: the job's `tags:` don't match the runner, untagged jobs are not allowed on it, or instance runners with another tag (for example `saas-linux-small-amd64`) pick them up. Compare the tags in the job log and in the runner settings, then fix `tags:` in `.gitlab-ci.yml` or disable instance runners for the project.
- **`permission denied … /var/run/docker.sock` in the runner log**: the runner process doesn't have the `docker` group. Check with the `ps -o user=,supgrp=` command above, then `sudo systemctl restart gitlab-runner`.
- **Runner fails to start after the switch to `gitlab-runner`**: `sudo journalctl -u gitlab-runner -n 30`. Usually a file in `/etc/gitlab-runner` still owned by root: `sudo chown -R gitlab-runner:gitlab-runner /etc/gitlab-runner`.
- **A monitoring container restarts with `permission denied`**: its data volume still belongs to the old container user. `sudo gitlab-runner/update.sh` hands the volumes to `monitoring` again.
- **`Cannot connect to the Docker daemon`**: Docker is stopped. `sudo systemctl status docker`, then `sudo journalctl -u docker --since "-10min"`.
- **`toomanyrequests` when pulling an image**: Docker Hub rate limit. Install the Docker Hub cache and check it with `curl -s 127.0.0.1:5000/v2/_catalog`.
- **Runner is offline in GitLab**: check `systemctl is-active gitlab-runner` and `sudo gitlab-runner verify`. If both are fine, the Hetzner Firewall may be blocking outbound HTTPS.
- **No logs in Grafana**: `health` shows whether Loki and Alloy are ready; `sudo docker compose -f /opt/logging/docker-compose.yml logs --tail 50 alloy` shows why Alloy isn't sending.
- **A component install failed**: the installer prints the cause and stops. Fix it and rerun the same command; installers back up what they change as `*.bak.<timestamp>`.
- **Disk full**: `dfd`, then the prune commands above. The weekly cleanup and the disk guard handle this automatically.

## Security notes

- The runner token is entered at the prompt and stored only in `/etc/gitlab-runner/config.toml` (`gitlab-runner`, mode `600`). Don't put it in user-data: anything on the server, including job containers, can read user-data through the metadata service.
- Job containers are not privileged. Enable `privileged = true` only for trusted projects that need Docker-in-Docker.
- Membership in the `docker` group is root-equivalent on the host. Only `gitlab-runner` has it, and Alloy gets the same access through `group_add` to read container logs. `health` warns if anyone else is in the group. Don't attach untrusted projects or forks to this runner.
- Monitoring, logging and the caches listen on `127.0.0.1` or the `docker0` bridge.
- Not done here, on purpose: rootless Docker and `userns-remap`, which change file ownership of bind mounts and runner caches, and a host firewall next to the Hetzner Cloud Firewall. Both are possible later; GitLab also suggests filtering access to the cloud metadata endpoint from job containers.

## Decommission

Delete the runner in GitLab, then delete the server **and** its Primary IPv4 in Hetzner. The IPv4 is billed separately even when unattached. Delete leftover snapshots too.
